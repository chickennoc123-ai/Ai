# ML-001-R2 TradingView Manual Parity Test Guide

**Purpose**: manual, human-in-the-loop verification that the Pine Script
implementation (`pine/ml_001_r2_features.pine`,
`pine/ML_001_R2_FEATURE_DEBUG.pine`, `pine/ML_001_R2_STRATEGY.pine`)
behaves consistently with the Python production pipeline
(`core/features/fe_r2_001.py`). This is **not** a production deployment
guide. No step here results in real trading.

**GOVERNANCE (unchanged by this guide)**: `ECONOMIC_VALIDITY = UNPROVEN`.
`PRODUCTION = BLOCKED`. `ML-001-R2 = RESEARCH_ONLY / NOT_AUTHORIZED`.
None of these scripts submit broker orders. Do not connect any of these
scripts to a broker, webhook, or auto-trading integration.

---

## 1. Setup

1. Open TradingView, select **EURUSD** (or **GBPUSD**) on the **1H (H1)**
   timeframe.
2. Open the Pine Editor, paste in `pine/ml_001_r2_features.pine`, click
   "Add to Chart." Confirm it **compiles without error** — this is the
   first, most basic parity check (structural: does the hand-authored
   Pine even parse under Pine v6). Repeat for
   `pine/ML_001_R2_FEATURE_DEBUG.pine` and `pine/ML_001_R2_STRATEGY.pine`.
3. On `ML_001_R2_FEATURE_DEBUG.pine`'s settings, leave **Debug Mode**
   checked (default) so the summary table appears top-right.
4. Scroll the chart left until at least 600 confirmed H1 bars are
   visible (needed for `volatility_regime` to leave its warmup window).

## 2. Inspecting live-chart values

For any bar, hover it — TradingView's **Data Window** (right-hand panel)
shows every `plot(..., display=display.data_window)` series at that
exact bar, including `bar_index`, `bar_time`, each feature's warmup flag,
and `ALL_WARMED_UP`. This is the precise per-bar inspection mechanism;
the visible chart plots (`momentum_5`, `momentum_20`, `rsi_14`, `atr_14`,
`volatility_regime`) are for pattern-level sanity, not exact-value
reading.

Record, for at least 10 bars of your choosing: `bar_index`, timestamp,
and all five feature values plus their warmup flags. Compare qualitative
shape against what you'd expect from the visible price action (e.g. RSI
rising during an uptrend) — this cannot be compared numerically against
Python, since TradingView's real EURUSD/GBPUSD price history will never
match the synthetic fixture below.

## 3. Fixture Replay Mode — genuine Pine-vs-Python numeric comparison

`ML_001_R2_FEATURE_DEBUG.pine` embeds the first 160 bars (bar_index
0–159) of `ML-001-R2-PINE-PARITY-FIXTURE.csv` — a synthetic OHLC series
generated by, and run through, the real production
`core/features/fe_r2_001.build_feature_matrix()` — as Pine array
literals. Enabling **Fixture Replay Mode** in the script's settings
recomputes the canonical formulas against those embedded bars (reusing
the same `f_seededWilder()` function as the live-chart computation) and
diffs the result against Python's own recorded values.

1. Enable **Fixture Replay Mode**.
2. Open the Data Window on any of the first 160 bars of **whatever
   chart you have loaded** (the fixture replay is keyed by `bar_index`,
   not by the chart's real price — it works on any symbol/timeframe with
   at least 160 bars of history).
3. Read off `[fixture] pine momentum_5` vs
   `[fixture] expected momentum_5 (Python)` vs `[fixture] diff momentum_5`
   (and the equivalent triplet for `momentum_20`, `rsi_14`, `atr_14`).
   `diff` should be `0` or extremely close to `0` at every bar.
4. After scrolling through at least the first 160 bars once (so the
   running max-diff accumulators have seen every embedded bar), check
   the summary table's **"fixture max|diff| (0-159)"** and **"fixture
   mismatches>tol"** columns. Tolerances are declared in the script
   itself (`TOL_MOMENTUM = 1e-7`, `TOL_RSI = 1e-4`, `TOL_ATR = 1e-7`) —
   fixed constants, not tuned after seeing results. A mismatch count of
   `0` for every feature is the pass condition.
5. `volatility_regime` is **not** covered by Fixture Replay Mode (its
   600-bar warmup exceeds what could safely be embedded as Pine array
   literals — see the script's own comments). Use the table in Section 4
   below to spot-check `volatility_regime` by timestamp instead, against
   the full CSV (`ML-001-R2-PINE-PARITY-FIXTURE.csv`, all 770 rows) if
   you separately load that CSV as a custom data feed.

**Note on bar 140/150 (flat-section RSI)**: `rsi_14` does not reset to
`50.0` merely because prices go flat — the seeded-Wilder recurrence
means `avg_gain`/`avg_loss` decay together, preserving whatever ratio
they had entering the flat section, unless the ENTIRE 100-bar warmup
window was flat from bar 0 (see
`tests/test_pine_parity.py::TestPhase9AdversarialScenarios::test_flat_market_zero_momentum_rsi_50_atr_zero`
for the isolated bar-0-onward case, where RSI does hit exactly `50.0`).
This fixture's flat section (bars ~120–150) follows a non-flat warmup
section, so RSI here is pinned near its pre-flat value, not 50 — this is
expected, correct behavior, not a defect.

## 5. Signal/execution timing (`ML_001_R2_STRATEGY.pine`)

`PINE_MODEL_STATUS = BLOCKED_BY_MISSING_MODEL_ARTIFACT` — no trained
RF-R2-001 model exists, so the real LONG/SHORT condition can never fire
and the Strategy Tester will always show **zero trades**. This is
correct, not a bug.

To visually confirm the SIGNAL BAR → EXECUTION BAR (T+1) marker
mechanism works independent of the (absent) model:

1. In the script's settings, enable **TIMING DEMONSTRATION MODE**
   (off by default). This drives a synthetic, non-economic pulse
   (`bar_index % 47 == 0`, past bar 600) — never a real signal, never
   wired to `strategy.entry`/`strategy.exit`.
2. Confirm a yellow up-triangle ("SIG") appears below the pulse bar, and
   a cyan down-triangle ("EXEC") appears above the very next bar — never
   the same bar.
3. Confirm the Strategy Tester's trade list remains empty throughout
   (proving the demo pulse never reaches order execution).

## 6. Recording discrepancies

For any mismatch you observe (either a compile error, or a Fixture
Replay Mode `diff` outside the declared tolerance, or a live-chart value
that looks structurally wrong — e.g. a warmup flag not clearing at the
expected bar), record: bar_index / timestamp, the feature name, Python's
expected value, Pine's actual value, and the absolute/relative
difference. Report this against
`ML-001-R2-PYTHON-PINE-PARITY-REPORT.md`'s verdict table — a confirmed
mismatch outside tolerance should flip the relevant `*_PARITY` field
from `PASS` to `FAIL`, not be silently absorbed.
