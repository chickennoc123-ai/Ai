## 3. Model artifact status (Phase 6)

```
PINE_MODEL_STATUS = BLOCKED_BY_MISSING_MODEL_ARTIFACT
```

No trained `RF-R2-001` model artifact (`.joblib` or otherwise) has ever
existed anywhere in this repository or its git history. This has been
independently confirmed at every prior phase of the ML-001-R2 project
(implementation, integrity audit, remediation rounds, economic
validation attempt) and was re-confirmed for this phase.

Spec §13 (PINE COMPATIBILITY ARCHITECTURE) mandates **Approach B**: an
automated exporter that translates the *trained* model's actual tree
structure into generated Pine code, tree-by-tree. **Approach C**
("replace Random Forest with a Pine-compatible model and call it
equivalent") is explicitly rejected by the spec itself, independent of
this project's own governance prohibitions.

Because no trained artifact exists:
- `pine/ml_001_r2_rf_export.pine` was **not created** — there is nothing
  to export, and hand-writing placeholder tree thresholds would violate
  both the spec and the governance prohibition against inventing a
  model.
- `ML_001_R2_STRATEGY.pine` hardcodes `modelReady = false` and leaves
  `p` (the model probability) permanently `na`. Every LONG/SHORT
  condition, and everything downstream of it (position sizing, SL/TP,
  exit logic), is therefore **structurally unreachable** — not just
  logically false, but code that Pine's own execution model can never
  enter given `modelReady`'s constant value.
- The Strategy Tester, if run, will show **zero trades** by
  construction. This is the correct, honest representation of "no
  model exists" — not a placeholder bug to be silently patched later
  with a substitute model.

## 4. Logical parity (Phase 9)

Eight adversarial scenarios were run against the real Python pipeline
(`tests/test_pine_parity.py::TestPhase9AdversarialScenarios`, 8 tests,
all passing): rising market, falling market, flat market, RSI extreme
(all-gains saturation), ATR spike-then-decay, volatility-regime
transition (low→high→low), insufficient warmup, and the T+1 timing
property. Each test's docstring states the exact behavior the (byte-
identical, per Section 2) Pine canonical block implies for that
scenario — this is a **traceable claim**, not something proven by
executing Pine, since no Pine compiler is available in this environment.

**A genuine, non-obvious finding surfaced while writing these tests**:
the seeded-Wilder RSI does not "reset" to 50 the instant a market goes
flat, nor does it snap to exactly 100 the instant a market becomes all
up-closes. `avg_gain`/`avg_loss` decay by the same multiplicative factor
(`×13/14` per bar) once their raw inputs become 0, so their **ratio is
inherited** from whatever it was before the flat/all-gains period began
— RSI stays pinned near its pre-transition value for a long time,
converging only asymptotically. Exact `RSI==50.0` or `RSI==100.0`
requires the flat/all-gains condition to hold for the *entire* 100-bar
warmup window, not just the recent past. Both adversarial tests were
corrected to construct that condition explicitly (see the corresponding
docstrings) rather than asserting a plausible-but-wrong intuition. Since
this is a property of the *shared* recurrence definition (spec §4, both
languages), it applies identically to Pine's `f_seededWilder()` — this
is not a Python-only quirk to reconcile against Pine, but a real,
correct property either implementation should also exhibit.

## 5. Numerical parity (Phase 7) and open ASSUMPTIONS

**What was verified by automated test** (`tests/test_pine_parity.py::TestFixtureEmbedTranscriptionCorrectness`, 9 tests, all passing):
the OHLC and expected-feature array literals embedded in
`ML_001_R2_FEATURE_DEBUG.pine` for bars 0–159 are exactly what
`ML-001-R2-PINE-PARITY-FIXTURE.csv` says they should be (tolerance
`5e-7`, tighter than the embed's own 6-decimal-place precision), and
the warmup boundaries (5/20/100/100 for momentum_5/momentum_20/
rsi_14/atr_14) match spec §4 exactly. This derisks the transcription
step — any live-TradingView discrepancy a human observes can be trusted
to reflect a real Pine-execution-semantics difference, not a copy error.

**What was NOT verified** — because no Pine compiler/runtime is
available in this authoring environment, the following remain
**documented ASSUMPTIONS**, each flagged in the relevant `.pine` file's
own comments, pending the manual test in
`ML-001-R2-TRADINGVIEW-MANUAL-TEST-GUIDE.md`:

1. `ta.percentile_linear_interpolation(source, length, percentage)`
   requires `length` consecutive defined bars before returning non-`na`
   (mirroring pandas' `rolling(..., min_periods=window)`) — not
   independently confirmed against Pine's actual documented/observed
   behavior.
2. Pine's floating-point arithmetic (`float`, effectively IEEE-754
   double per TradingView documentation) matches Python/NumPy `float64`
   closely enough that the declared tolerances (`1e-7` momentum/ATR,
   `1e-4` RSI) hold in a real 770+-bar run, not just the 160-bar embed.
3. The position-sizing formula's price-distance reformulation (Section
   2's §10 row) is algebraically equivalent to the spec's literal
   pips/pip-value formulation for Pine's `strategy.entry(qty=...)` — not
   independently confirmed against a specific broker's pip/lot
   convention, and moot at present since this code path is unreachable.

`MAX_NUMERICAL_ERROR` observed in this report's own automated testing
(fixture-embed transcription, 160 bars × 4 features = up to 640
comparisons): **0** mismatches above the declared `5e-7` tolerance.
This number describes transcription accuracy, not a live Pine-vs-Python
run (which has not occurred).

## 6. Timing parity / no-repaint audit (Phase 12)

- **No `request.security()` used anywhere** in any of the three `.pine`
  files — all computation operates on the chart's own symbol/timeframe
  series (`close`/`high`/`low`/`open`/`bar_index`/`time`). There is
  therefore no multi-context lookahead/repainting risk of the kind
  `request.security()` can introduce; none was needed since this is a
  single-symbol, single-timeframe script.
- **No lookahead**: every historical reference in the canonical block is
  `close[n]`/`high[n]`/`low[n]` for `n ≥ 0` (current bar or strictly
  past bars) — no negative-index (future) reference exists anywhere.
- **`ML_001_R2_STRATEGY.pine`'s realtime-bar behavior**: declared with
  `calc_on_every_tick = false`, so entry/exit conditions are evaluated
  once per bar close (including the realtime/forming bar), not on every
  intrabar tick — preventing a signal from firing on partial/unconfirmed
  data.
- **T+1 execution, cross-checked two ways**: (a) the manual
  `pendingExecution`/`executionBar` marker used for the visual SIGNAL/
  EXECUTION-bar demo, and (b) Pine's native `process_orders_on_close =
  false` fill semantics (any `strategy.entry`/`strategy.exit` invoked
  during bar t's evaluation fills at bar t+1's open, automatically).
  These are two independently-implemented mechanisms for the same T+1
  invariant; both are present and neither contradicts the other in the
  source, though this has not been confirmed by an actual TradingView
  run (`tests/test_pine_parity.py::test_signal_on_close_then_execution_next_bar_is_a_pine_native_property`
  checks the strategy() declaration's settings only, not runtime
  behavior).
